## What caused the prior failure

On 2026-06-03 the user uploaded 15 new 2.92mm-F shots, then 21 more
reticle-crop 2.92mm-F shots later in the day. v9 had been kicked at 04:30 EDT
and finished before any of those uploads existed. So v7+v9 (which had been
deployed at 05:01 EDT) was confidently wrong on the user's actual workflow —
it had never seen the kind of frames the user was producing.

Per-image inspection showed v9 confidently called these 2.92mm-F shots
"3.5mm-F" at 0.92-0.95 conf. v7 alone shared the same error pattern
(correlated mistakes), so ensembling didn't help — disagreement abstention
caught nothing.

## What unlocked v10

`combined_v10_2026-06-03` snapshot = `combined_v9` train (3,678) + 39 new
2026-06-03 corrections (incl. 15 + 21 new 2.92mm-F uploads). Total 3,738
samples. 2.92mm-F class grew from **153 → 189** training samples.

Same recipe as v7/v9 (EffNetV2-S, scale=(0.20, 1.0), lr 1e-4, batch 16,
50 epochs, seed 0). Trained 2026-06-03 13:56 EDT → 16:18 EDT (~2.5h). Best
epoch 24, val_acc 0.946.

The fix is **purely data** — the model architecture, recipe, and inference
pipeline are unchanged from v7. Adding 21 distance-varied 2.92mm-F shots
moved the 2.92mm-F decision boundary enough to recover the user's failure
mode.

## Why ensemble vs v10 alone

v10 alone:
- today: **4 CW** (huge improvement vs v7's 19 alone, but not zero)
- phone-v2: **1 CW**
- hard_292F: 1 CW
- close-up: 4 CW (regression vs v7's 3)

v10 alone is too aggressive in some directions and regresses on phone-v2 and
close-up. v7+v10 ensemble combines v10's new fine-pitch capability with v7's
stability everywhere else → zero CW on all realistic-distance sets.

## What didn't matter — the Sonnet vision audit

On 2026-06-04 a parallel investigation ran a Sonnet vision audit across all
4 female training classes (1,020 imgs across 2.92mm-F, 3.5mm-F, 2.4mm-F,
1.85mm-F) plus sample batches of the M classes. **Result: 0 wrong-gender
mislabels found.** Sonnet caught 12 JUNK files (wood-grain-only, severely
blurred) which were moved to `_deleted/`.

Conclusion: the training labels were already clean. The 2.92mm-F bug was not
a data-quality issue; it was a data-volume gap on a specific class. Sonnet
vision **cannot** distinguish 2.92mm vs 3.5mm vs 2.4mm (sub-millimeter size
differences invisible without a reference scale), so it can only flag gender
mistakes — which there were none of.

A small cluster of suspicious agg_0258-0278 in `1.85mm-M/` was flagged as
possibly female. User-facing compare gallery deployed at
`https://aired.com/compare185/` (per-image side-by-side with reference F + M,
buttons for Delete / Keep / Flip). User reviewed; the agg_026x files are
actually duplicates that exist in both `1.85mm-M/` and `1.85mm-F/` —
removing the M copies is safe (the F copies are correct). Mostly not yet
acted on (only `agg_0258` removed during a debug test). The duplicates do
not appear to harm v10 enough to matter.

## Deploy mechanics

Single env-var change. No code changes. No service restart of nginx, no
reboot. Same backup-then-sed-then-restart pattern as v7+v9 deploy.

```bash
sudo cp /etc/default/rfcai-predict /etc/default/rfcai-predict.bak.2026-06-05-v7v10winner
sudo sed -i "s|^RFCAI_JERRY_EXTRA_MODEL_DIRS=.*|RFCAI_JERRY_EXTRA_MODEL_DIRS=/home/rfcai/training/models/jerry_v19_hybrid_combined_v10_2026-06-03|" /etc/default/rfcai-predict
sudo systemctl restart rfcai-predict
```

Post-deploy smoke test on box:
- 4 of 5 phone-realistic 3.5mm-M shots → `3.5mm-M @ 0.86-0.96` ✓
- 1 (the persistent dup8 hard case) → `2.92mm-M @ 0.55` (abstains in app)
- 3 of 3 hard 2.92mm-F shots → `2.92mm-F @ 0.48` (correct class, below threshold = abstain in app — no CW)

## Rollback

```bash
sudo cp /etc/default/rfcai-predict.bak.2026-06-05-v7v10winner /etc/default/rfcai-predict
sudo systemctl restart rfcai-predict
```

Restores v7+v9 ensemble. v7 single-model rollback also still available via
`.bak.2026-05-28-v7winner`.
